# 1. 조회 요청과 화면 상태 관리

## 1.1 조회 결과에 따른 화면 상태

조회 결과에 따라 로딩, 빈 결과, 정상 결과, 오류 화면을 구분한다.

| 상태 | 발생 조건 | 화면 처리 |
|---|---|---|
| 로딩 | 조회 요청 후 응답 대기 중 | 스켈레톤 또는 로딩 표시 |
| 빈 결과 | 요청 성공, 조회 결과 0건 | 빈 결과 안내 표시 |
| 정상 결과 | 요청 성공, 상품 1건 이상 | 조회된 상품 목록 표시 |
| 오류 | 네트워크 오류 등으로 조회 실패 | 오류 안내 및 재시도 제공 |

- **⚙️ 정상 조회 결과가 0건인 경우 오류로 처리하지 않는다.**
- **⚙️ 상품 2개 조회에 성공한 경우 실제 조회된 상품 2개를 목록에 표시한다.**
- 조회 중에는 사용자에게 로딩 상태를 안내한다.

## 1.2 로딩 및 빈 결과 안내

- 💬 [상품을 불러오는 중입니다.]
- 💬 [검색 결과가 없습니다. "[검색어]"에 대한 결과가 없습니다. 다른 검색어로 시도해보세요.]
- 💬 [원하는 상품을 찾지 못했나요? 다른 검색어나 카테고리를 이용해보세요.]

※ ❓ 결정 필요
- 최초 진입 시 스켈레톤 화면과 스피너 중 어떤 방식을 사용할지 결정
  - 스켈레톤: 상품 목록의 예상 구조를 먼저 표시
  - 스피너: 로딩 아이콘으로 대기 상태 표시
- 조회 결과가 없을 때 검색어 기반 안내와 일반 빈 결과 안내 중 어떤 문구를 사용할지 화면별로 결정

## 1.3 재조회 중 기존 화면 유지

재조회 요청 시 기존 목록을 유지할지 여부를 결정한다.

※ ❓ 결정 필요
- A. 기존 목록을 유지하면서 갱신 중임을 표시
- B. 기존 목록을 숨기고 로딩 화면 표시

검색어 변경, 새로고침 등 요청 목적에 따라 다른 방식을 적용할지 결정한다.

## 1.4 늦게 도착한 응답의 처리

- **⚙️ 이전에 보낸 요청의 응답이 늦게 도착하더라도 최신 요청의 결과를 덮어쓰지 않는다.**
- **⚙️ 최신 요청과 이전 요청의 응답 도착 순서가 달라질 수 있으므로 요청의 유효성을 확인한 후 화면에 반영한다.**

예시:

1. 검색 요청 `R10` 전송
2. 이후 검색 요청 `R12` 전송
3. `R12` 응답 성공: 상품 `1001`, `1002` 표시
4. 이전 요청 `R10`의 응답이 늦게 도착
5. `R10`의 결과는 반영하지 않고 `R12`의 최신 결과 유지

## 1.5 ✅ 조회 상태 검증 시나리오

- [ ] 조회 요청 직후 로딩 화면이 표시되는지 확인
- [ ] 조회 성공 후 결과가 0건이면 빈 결과 화면이 표시되는지 확인
- [ ] 조회 성공 후 상품 2개가 반환되면 상품 2개가 표시되는지 확인
- [ ] 상품이 표시된 상태에서 이전 요청의 응답이 늦게 도착해도 최신 결과가 유지되는지 확인
- [ ] 빈 결과를 오류 화면으로 잘못 표시하지 않는지 확인

# 2. 통신 오류와 화면 복구

## 2.1 네트워크 오류 처리

- ⚠️ 통신 실패 시 오류 상태를 표시한다.
- 사용자가 재시도할 수 있도록 안내한다.
- **⚙️ 재시도하더라도 검색어, 입력값 등 사용자가 작성한 내용을 유지한다.**
- **⚙️ 오류가 발생했다는 이유만으로 입력값이나 기존 작업 내용을 초기화하지 않는다.**

※ ❓ 결정 필요
- 조회 요청 실패 시 자동 재시도를 허용할지 결정
- 자동 재시도 허용 시 최대 횟수, 재시도 간격 및 대기 시간 증가 방식 결정
- 자동 재시도 실패 후 사용자에게 수동 재시도를 제공할지 결정
- 재조회 중 기존 목록을 유지하는 경우 오류 발생 후에도 기존 목록을 유지할지 결정

## 2.2 화면별 오류 및 복귀 처리

오류가 발생한 화면과 사용자의 작업 목적에 따라 복구 방법을 정의한다.

| 상황 | 처리 기준 |
|---|---|
| 검색 오류 | 검색어를 유지하고 재시도할 수 있도록 안내 |
| 주문서 작성 중 통신 끊김 | 입력한 배송지, 요청 사항 등 작성 내용 유지 |
| 위치 권한 거부 | 권한 거부 상태를 안내하고 가능한 대체 경로 제공 |
| 통신 오류로 화면 진입 실패 | 이전 화면 또는 해당 화면에서 재시도할 수 있도록 처리 |

※ ❓ 결정 필요
- 각 오류 발생 시 현재 화면에 남을지, 이전 화면으로 돌아갈지 결정
- 위치 권한 거부 시 주소 직접 입력 등 대체 경로 제공 여부 결정
- 화면 복귀 시 검색 조건, 스크롤 위치, 입력값을 어디까지 유지할지 결정
- 오류 발생 후 로그인이나 다른 화면으로 이동해야 하는 조건 및 복귀 경로 결정

## 2.3 ✅ 오류 복구 검증 시나리오

- [ ] 통신 실패 후 재시도할 때 검색어와 입력값이 유지되는지 확인
- [ ] 주문서 작성 중 연결이 끊겨도 작성 내용이 유지되는지 확인
- [ ] 위치 권한을 거부한 경우 적절한 안내와 대체 경로가 제공되는지 확인
- [ ] 오류 후 현재 화면 유지 또는 이전 화면 복귀가 정의된 정책에 따라 동작하는지 확인
- [ ] 지속적인 통신 실패 시 무한 재시도가 발생하지 않는지 확인

# 3. 가격 조회와 결제 전 재검증

## 3.1 가격 캐시 처리

- **⚙️ 이전에 조회한 가격이 캐시에 있더라도 현재 가격이 확정되었다고 간주하지 않는다.**
- 가격 정보가 캐시에만 존재하고 최신 가격을 확인하지 못한 경우 `확인 중` 상태로 표시한다.
- 화면에 표시된 가격이 최신 가격과 다를 수 있음을 고려한다.

## 3.2 결제 직전 가격 재검증

- **⚙️ 결제 직전에 현재 가격을 다시 확인한다.**
- **⚙️ 가격 재검증이 완료되기 전에는 기존 캐시 가격만으로 결제를 확정하지 않는다.**
- 최신 가격을 확인한 후 최종 결제 금액을 반영한다.

※ ❓ 결정 필요
- 가격 조회 실패 시 결제 진행을 차단할지 결정
- 기존 가격과 최신 가격이 다른 경우 사용자에게 변경 금액을 안내하고 재확인받을지 결정
- 가격 확인 중 로딩 표시 및 재시도 정책 결정

## 3.3 ✅ 가격 및 결제 검증 시나리오

- [ ] 캐시 가격만 존재하는 경우 가격을 `확인 중`으로 표시하는지 확인
- [ ] 결제 직전에 최신 가격을 재조회하는지 확인
- [ ] 최신 가격 확인 전 캐시 가격만으로 결제가 확정되지 않는지 확인
- [ ] 가격 변경 시 최종 결제 금액이 최신 가격에 맞게 반영되는지 확인
- [ ] 가격 조회에 실패한 경우 정의된 결제 제한 정책이 적용되는지 확인

# 4. 공통 접근성 정책

## 4.1 글자 확대 및 화면 구성

- 고객 설정에서 큰 글자 모드를 지원한다.
- 글자 확대 시에도 상품 정보, 주문서 금액, 결제 버튼 및 오류 메시지가 잘리지 않아야 한다.
- 화면 크기와 글자 크기가 변경되어도 주요 기능을 사용할 수 있어야 한다.

## 4.2 스크린리더 안내

- **⚙️ 화면 상태가 변경되면 스크린리더로 해당 상태를 안내한다.**
- 안내 대상은 다음과 같다.
  - 로딩 시작
  - 조회 성공 및 빈 결과
  - 조회된 상품 목록의 개수
  - 네트워크 오류
  - 재시도 가능 여부 등 주요 안내 정보

## 4.3 버튼 및 오류 안내 접근성

- 버튼은 스크린리더가 기능을 이해할 수 있는 이름으로 안내한다.
- 버튼과 주요 조작 요소는 충분한 터치 영역을 제공한다.
- **⚙️ 색상만으로 상태를 구분하지 않고 텍스트 또는 보조기기 안내를 함께 제공한다.**
- 품절 상품은 버튼을 비활성화하고, 품절 상태를 텍스트로 표시한다.
- 💬 [품절되었습니다.]
- 입력 오류가 발생하면 오류 메시지를 표시하고, 필요에 따라 오류가 발생한 입력 필드로 초점을 이동한다.

## 4.4 ✅ 접근성 검증 시나리오

- [ ] 큰 글자 모드에서 주문서 금액, 결제 버튼 및 오류 메시지가 잘리지 않는지 확인
- [ ] 로딩 시작 시 스크린리더가 로딩 상태를 안내하는지 확인
- [ ] 조회 성공 시 빈 결과 또는 상품 목록 개수를 안내하는지 확인
- [ ] 네트워크 오류 발생 시 스크린리더가 오류 상태를 안내하는지 확인
- [ ] 버튼의 이름과 기능이 스크린리더로 전달되는지 확인
- [ ] 품절 상태가 색상뿐 아니라 텍스트와 스크린리더로 구분되는지 확인
- [ ] 입력 오류 발생 시 오류 메시지를 확인할 수 있고 초점 이동이 적절하게 이루어지는지 확인

# 5. 결제 및 기타 요청의 재시도 정책

## 5.1 일반 조회와 금전 처리 구분

- 일반 조회 요청은 재시도를 통해 최신 결과를 다시 확인할 수 있다.
- 결제 등 금전 처리는 요청이 실패한 것처럼 보여도 실제 처리 결과가 확정되지 않았을 수 있다.
- **⚙️ 결제 결과를 먼저 확인한 후 재시도해야 한다.**
- **⚙️ 결제 성공 여부가 확인되지 않은 상태에서 동일한 결제 요청을 무조건 다시 전송하지 않는다.**

※ ❓ 결정 필요
- 일반 조회의 자동 재시도 허용 범위 및 횟수
- 결제 결과 확인 방법과 결과 조회 실패 시 처리 방식
- 결제 결과가 불명확한 경우 사용자에게 표시할 안내 문구
- 중복 결제 방지를 위한 요청 식별 및 중복 처리 기준

## 5.2 ✅ 재시도 정책 검증 시나리오

- [ ] 일반 조회 오류 시 정의된 재시도 정책이 적용되는지 확인
- [ ] 결제 요청 후 통신이 끊긴 경우 결제 결과를 먼저 확인하는지 확인
- [ ] 결제 성공 여부가 확인되지 않은 상태에서 중복 결제가 발생하지 않는지 확인
- [ ] 결제 결과 조회에 실패한 경우 정의된 안내 및 복구 경로가 제공되는지 확인
