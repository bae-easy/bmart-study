# 고객앱 업무 흐름 정리 (장바구니)

> **범위:** 장바구니 → 주문서 → 결제 → 배송·주문 알림 → 반품·교환  
> **프로젝트 변경 정책(2026-10-15):** 상품은 목록·상세에서 장바구니에 추가하며, 실제 재고 및 배송 시간 확정 반영은 결제 완료 시점이다. 최소 주문금액은 15,000원이고, 상품 합계 30,000원 이상 또는 첫 구매면 배달팁 무료로 처리한다. 봉투값은 주문당 100원 고정, 주문 완료 후 정보 변경 및 회수지 변경은 허용하지 않는다. 반품 화면의 9,000원은 반품 배달비 옵션 구매 흐름으로 해석한다. **상품당 기본 최대 구매 수량은 10개이며 상품별로 다를 수 있다. 주문 상품 총중량이 10kg을 초과하면 분할배송한다.**
> **작성 기준:** 화면에서 관찰한 동작은 **화면 관찰**로, 문서에 확정된 항목은 **프로젝트 결정**으로, 추가 설계는 **구현 제안**으로, 합의가 필요한 항목은 **미결정**으로 구분한다. 캡처의 가격·혜택·시간은 촬영 당시 화면의 예시이며 현재 서비스의 고정 정책으로 해석하지 않는다.

## 1. 전체 흐름

```mermaid
flowchart TD
    A[상품을 장바구니에 담기] --> B[장바구니 상품·수량 확인]
    B --> C{최소 주문금액 충족?}
    C -->|아니요| B
    C -->|예| D[배송 방식 선택]
    D --> E{예약배달인가?}
    E -->|예| F[날짜·도착 시간대 선택]
    E -->|아니요| G[주문 진행]
    F --> G
    G --> H[마지막으로 둘러보기]
    H --> I[주문서: 주소·연락처·요청사항]
    I --> J[혜택·최종 금액 확인]
    J --> K[토스페이먼츠 결제 인증]
    K --> L[서버 결제 승인·검증]
    L --> M{승인 결과}
    M -->|성공| N[결제 완료·주문 처리]
    M -->|실패| O[오류 안내·재시도 판단]
    M -->|불명확| P[상태 조회 후 확인]
    N --> X{총중량 10kg 초과?}
    X -->|예| Y[분할배송 건 생성]
    X -->|아니요| Z[단일 배송 건 생성]
    Y --> Q[피킹·패킹·배송·전달완료]
    Z --> Q
    Q --> R[주문 내역·알림 확인]
    R --> S{사후 처리 필요?}
    S -->|반품| T[고객센터 반품·환불]
    S -->|교환| U[교환 신청·회수·재배달]
```

**핵심 구분**

- **장바구니:** 살 상품·수량·배송 방식을 선택하고 주문 가능 여부를 확인한다. 상품별 기본 구매 제한은 10개다(상품별 상이).
- **주문서:** 배송지·라이더 요청·연락처·품절 시 처리·혜택·결제 금액을 최종 확인한다.
- **결제:** 결제창 복귀와 별개로 **서버 승인 결과를 확인한 뒤** 주문을 완료한다.
- **배송과 알림:** 주문 상태와 고객에게 발송한 알림 내역을 구분한다. 총중량 10kg 초과 주문은 배송 건을 분리하되 원 주문번호·결제는 유지한다.
- **사후 처리:** 반품은 고객센터 접수 방식으로 기술되어 있고 (실제 B마트에서 선택 불가능), 교환은 별도의 신청·회수·재배달 흐름이 있다.

## 2. 장바구니

### 2.0 상품 목록·상세에서 장바구니에 상품 추가

**고객앱 기본 흐름**

1. 고객은 **상품 목록에서 상품 추가(담기) 버튼**을 누르거나, **상품 상세 페이지에서 상품·옵션·수량을 확인한 뒤 장바구니에 담을 수 있다.**
2. 상품을 추가한 이후 장바구니에서 담은 상품을 확인하고 주문할 품목·수량을 조정한다.
3. 상품 목록에서 담기를 제공하지 않는 품목은 상세 접근 또는 별도 인증을 먼저 요구할 수 있다.
4. **상품당 기본 구매 수량 제한은 10개**로 설정한다. 단, 실제 적용 상한은 상품에 설정된 제한 수량이 우선하며, 목록·상세·장바구니·주문서·서버에서 동일하게 검증한다.
5. 장바구니 수량 변경은 고객의 주문 의사 표시이며, **재고 차감 및 배송 시간의 최종 확정은 결제 완료 시점**에 반영한다. 결제 전에는 재고·주문 가능 시간에 변경이 생길 수 있다.

**일부 성인인증 상품 화면 사례**

### 2.1.1 상품별 구매 수량 제한 

- 한 상품을 한 주문에서 구매할 수 있는 **기본 상한은 10개**다. 예를 들어 상품에 5개 상한이 등록되어 있다면 5개까지만 구매한다.
- 상품 목록·상세의 담기 버튼, 장바구니 `+` 버튼, 주문서 재검증, 서버 주문 생성 요청에 같은 상한을 적용한다.
- 상한 도달 시 추가 수량 변경을 막고 고객에게 제한 수량을 안내한다. 네트워크 요청에서 임의로 11개 이상을 보내더라도 서버에서 거부한다.
- 구매 수량 상한은 **재고 수량**과 다르다. 사용 가능한 재고가 더 적으면 실제 담기 가능 수량은 `min(상품별 구매상한, 현재 주문 가능 재고)`가 된다.
- **구현 제안:** `products.max_order_qty INT NOT NULL DEFAULT 10`을 사용해 상품별 설정한다. 옵션 단위 제한 또는 고객별 구매 제한은 별도 정책 결정이 필요하다.

### 2.2 배송 방식 선택과 금액 확인

장바구니 하단에서 수령 방법을 선택한다. 이 문서에서는 화면의 **수령 방법**을 업무 용어인 **배송 방식**으로 함께 표기한다.

![배송 방식 선택](images/image-3.png)

- **한집배달:** 예상 소요 시간과 배달팁을 확인한다.
- **알뜰배달:** 예상 소요 시간과 배달팁을 확인한다.
- **예약배달:** 원하는 도착 시간대를 선택해야 한다.
- 배송 방식에 따라 화면의 배달팁·할인·예상 도착 정보가 변경될 수 있다.

![주문 예상 금액과 혜택 표시](images/image-4.png)

**금액 구조**

```text
상품금액
+ 배달팁(무료 조건 충족 시 0원)
+ 봉투값(100원 고정)
- 상품 할인
- 쿠폰/기타 적용 혜택
= 최종 결제 금액
```

- 금액은 선택된 상품과 실제 적용 가능한 할인 기준으로 다시 계산한다. 
- 봉투값은 주문당 100원 고정으로 합계에 포함한다. 
- 배달팁은 배송 방식별 기준요금에서 무료 조건을 판정한다. 
- 첨부 화면의 880원, 28,480원 등은 **화면 예시**이다. 
- 상품금액·배달팁·할인액은 주문서와 결제 직전에 재확인한다.

### 2.3 주문 가능 여부 검사

| 상태 | 화면 동작 |
|---|---|
| 최소 주문금액 미충족 | 부족 금액 안내, 주문 버튼 비활성화 |
| 최소 주문금액 충족 + 배송 방식 미선택 | `수령방법을 선택해주세요` 표시, 누르면 배송 방식 영역으로 스크롤 |
| 최소 주문금액 충족 + 배송 방식 선택 완료 | 선택 방식에 맞는 `주문하기` 버튼 활성화 |
| 예약배달을 선택했으나 시간 미선택 | 예약 시간 선택을 요구 |

## 3. 주문서

### 3.1 주문서 진입 전: 마지막으로 둘러보기

장바구니에서 주문하기를 누르면 **`마지막으로 둘러보기`** 상품 추천 화면이 나타나는 사례가 확인된다.

- 재주문 많은 상품
- 1만원 이하 상품

> **중요:** 배달팁 안내 팝업에는 주문 금액뿐 아니라 거리·시간대·지역·할인·요금제 등의 영향을 받을 수 있다고 설명한다. 원본 화면의 특정 금액이나 할인 기간은 촬영 당시의 사례다. **실제 프로젝트에서 적용할 배달팁은 배달 방식별 기본 요금이 고정되는 것으로 정한다.**

> **적용 우선순위:** 배송 방식 기준 배달팁 산출 → 첫 구매 또는 주문금액 30,000원 이상 여부 확인 → 조건을 충족하면 배달팁 0원 → 봉투값 100원 더하기. 두 무료 조건은 중첩하여 추가 할인을 만들지 않는다.

> **예시(설명용):** 상품금액 30,000원, 할인 0원, 배달팁 무료 조건 충족 시 `30,000 + 배달팁 0 + 봉투값 100 = 30,100원`이다. 할인 상품의 최소 주문금액·무료 배송 산정 기준을 할인 전/후 어느 금액으로 볼지는 팀에서 최종 확정해야 한다.

> **법령 표현 주의:** 일회용 봉투의 유상 제공 제도와 별개로, **100원이라는 액수는 이 프로젝트에서 정한 고정값**으로 기록한다. 정부가 모든 서비스에 100원이라는 동일 금액을 강제한다고 단정하지 않는다.

## 4. 결제 및 결제 예외 처리

### 4.1 기본 결제 흐름

```mermaid
sequenceDiagram
    actor 고객
    participant 앱 as 고객앱
    participant 서버 as 주문/결제 서버
    participant PG as 토스페이먼츠
    고객->>앱: 결제하기
    앱->>서버: 결제할 주문 확인 요청
    서버->>서버: 재고·가격·배송·할인 검증
    서버-->>앱: 주문번호·서버 확정 금액
    앱->>PG: 결제 인증 진행
    PG-->>앱: 결제 인증 결과
    앱->>서버: 인증 정보 전달
    서버->>PG: 결제 승인 요청
    PG-->>서버: 승인 성공/실패/확인 필요
    서버->>서버: 결제 상태와 주문 상태 반영
    서버-->>앱: 최종 결과
    앱-->>고객: 완료 또는 오류 안내
```

- 결제창에서 돌아왔다고 해서 자동으로 `결제 완료`가 되는 것은 아니다.
- 서버에서 `orderId`·결제 금액을 검증한 뒤 승인한다.
- 승인 성공 뒤 주문·결제 상태를 저장하고 고객에게 완료 화면을 제공한다.
- 승인 상태를 모르는 경우 실패라고 단정하거나 즉시 새 결제를 만들지 않는다.

### 4.2 주문·결제 데이터

| 주문 데이터 | 결제 데이터 |
|---|---|
| 주문번호, 주문상품·수량 | `orderId`, `paymentKey` |
| 상품 금액·할인 금액·배달팁 | 요청/승인 금액, 결제 수단 |
| 최종 결제 금액, 주문 상태 | 결제 상태, 승인 일시 |
| 배송지·배송방식·예약시간 | 취소 금액·사유·거래 이력 |

### 4.3 성공·실패·불명확 상태

| 상황 | 처리 |
|---|---|
| 승인 성공 | 결제 상태 완료 → 주문 처리 단계 진행 → 고객에게 완료 안내 |
| 승인 실패 | 완료로 처리하지 않음 → 원인 안내 → 재시도 가능 여부 판단 |
| 인증 후 결과 확인 실패 | 결제 조회를 통해 실제 승인 여부 확인, 무분별한 재결제 차단 |
| 중복 결제 요청 | 기존 주문·결제 상태 확인, 중복 승인 방지 |
| 금액 불일치 | 서버 계산액과 승인 요청액을 비교, 불일치 시 승인 중단 및 금액 재확인 |
| 승인/취소 통신 오류 | 최종 처리 여부 재조회 후 상태 확정, 멱등성 처리 검토 |

### 4.4 취소 및 환불 연동

1. 결제 전 주문 취소와 승인 후 취소를 구분한다.
2. 승인 후 주문 취소 시 현재 주문 상태와 취소 가능 여부를 확인한다.
3. 결제 취소의 성공 여부를 확인한 뒤 주문·결제 상태를 갱신한다.
4. 취소 오류가 발생한 경우에도 처리 결과를 조회한 뒤 재시도한다.
5. 프로젝트에서 **부분 결제취소를 지원하지 않기로 한 점**과 품절 상품 부분 취소/반품에 따른 정산을 함께 고려해야 한다.

### 4.5 보안과 확정된 범위

- 시크릿 키는 서버에서만 보관한다.
- 클라이언트에 노출되는 결제 금액은 신뢰하지 않고 서버 금액으로 비교한다.
- 승인·취소 요청 결과를 이력으로 남긴다.

**결정 완료:** 토스페이먼츠 **주문서형** 적용, **토스 외 결제 수단 미지원**, **부분 결제취소 미지원**.

참고: [토스페이먼츠 개발자센터](https://docs.tosspayments.com/) · [결제 API](https://docs.tosspayments.com/reference)

## 5. 배송 방식 및 예약배송

### 5.1 배송 방식 비교

| 구분 | 한집배달 | 알뜰배달 | 예약배달 |
|---|---|---|---|
| 고객 선택 | 즉시형 | 즉시형 | 도착 시간대 지정 |
| 도착 정보 | n~n분 후 | n~n분 후 | 선택된 날짜·시간대 |
| 기본 배달팁 | 4,000원 | 3,000원 | 3,000원 |
| 추가 동작 | 배송 방식 선택 | 배송 방식 선택 | 예약 날짜·시간 선택 |

- **별도 추가 배달팁 없음**
- **프로젝트 결정:** 첫 구매이거나 장바구니 주문 대상 상품 합계가 **30,000원 이상**이면 배달팁을 무료(0원)로 적용한다. 이 조건은 배송 방식 기본요금보다 우선한다.
- **프로젝트 결정:** 봉투값 **100원**은 배달팁 무료 여부와 관계없이 부과한다.
- 캡처에는 할인 적용으로 배달팁 **0원**이 표시된 사례도 있다. 표의 금액을 할인 전제와 무관한 절대 금액으로 처리하지 않는다.
- **00:00~08:00에는 예약배달만 가능**

### 5.1.1 총중량 10kg 초과 시 분할배송 (프로젝트 결정)

1. 주문 품목마다 `단위중량(g) × 주문 수량`을 계산하고 전부 합산한다.
2. **총중량이 10,000g 이하**면 원칙적으로 배송 건 1개를 생성한다. **10,000g 초과**면 배송 건을 최소 2개 이상 생성한다. `10,000g` 정확히는 초과가 아니므로 이 규칙에 의한 분할 대상이 아니다.
3. 분할된 각 배송 건에는 서로 다른 `shipment_id`를 부여하고 `order_id`는 동일하게 유지한다. 한 주문의 품목·수량을 여러 배송 건에 배정할 수 있어야 한다.
4. 각 배송 건의 합산 상품 중량이 10,000g을 넘지 않도록 배분하고, 피킹·패킹·배차·라이더 인계·배송완료를 배송 건별로 관리한다.
5. 주문서/배송현황에는 고객이 **한 주문이 여러 번 나뉘어 도착할 수 있음**을 알 수 있게 총 배송 건수, 각 배송 건 상태, 예상 정보를 표시한다.
6. 배송 완료 처리는 배송 건별로 먼저 저장하고, **모든 배송 건이 완료된 경우에만 주문 전체를 배송완료**로 집계한다.

> **산정 예시:** 2kg 상품 6개 = 12,000g → 배송 1/2(5개, 10,000g), 배송 2/2(1개, 2,000g). 고객 주문 1건·토스 결제 1건은 그대로 유지한다.

주문 확정 시 품목 중량 스냅샷을 저장하고 배송 건/배정 품목을 트랜잭션으로 생성한다. 부분 피킹 실패, 재배차, 미배송, 회수는 개별 배송 건 단위로 추적한다.

**미결정:** 포장재 중량 포함 기준, 상품 1개가 10kg 초과인 경우의 처리, 냉장·냉동 혼합 배정 방식, 분할배송 시 추가 배달비 부과 여부, 배송 건마다 다른 도착 시간 허용 범위. 이 항목들은 임의로 고정하지 않는다.

### 5.2 예약배달 시간 선택

1. 장바구니에서 예약배달 선택
2. 시간 선택 팝업 열기
3. 오늘/내일 중 날짜 선택
4. 조회된 **1시간 단위** 도착 시간대 중 하나 선택
5. 선택 완료 → 장바구니에 선택 내용 반영
6. 주문서 진입과 결제 요청 직전에 시간대 재검증

### 5.3 마감·변경·조회 오류

| 상황 | 처리 |
|---|---|
| 선택한 시간대가 마감됨 | 해당 시간대 비활성화, 다른 시간 재선택 안내 |
| 전체 시간대가 마감됨 | 선택 불가 안내, 필요하면 다른 날짜/재조회 제공 |
| 배송지 변경 | 새 배송지 기준 가능 시간 재조회 |
| 시간대 조회 오류 | 오류 안내, 조회 실패한 시간을 유효 시간으로 확정하지 않음 |
| 장바구니 상품 조회 오류 | 상품을 불러오지 못했다는 안내와 확인 후 재조회 사례 기록 |

**운영 메모:** 조회 오류 시 자동 재시도는 하지 않는다 (B마트에서 확인한 방식). 이전 시간대 임시 표시 허용 조건도 적혀 있으나, **조회 실패 시 주문 진행 허용 여부**는 원문에 결정 결과 없이 남아 있어 미결정으로 분리한다.

### 5.4 주문 완료 후 배송현황 화면과 상태별 이동

주문완료 후 배송현황 진입 시 로딩이 표시되고, 주문 확인 화면에서 상태 진행 바·지도·배송지·주문 정보를 조회할 수 있다. 예약 주문의 경우 선택한 도착 예정 시간대가 표시된다.

<img src="images/screenshots/tracking-order-confirmed.jpg" alt="주문 확인 단계 배송현황" width="400">

<img src="images/screenshots/tracking-reserved.jpg" alt="예약배송 현황 및 도착 시간대" width="400">

**배송 과정의 화면 흐름**

1. **주문확인:** 주문 접수 및 처리 준비 단계 표시, 배송정보 자세히 보기 제공.
2. **배송예약:** 확정된 예약 도착 시간대 표시. 이 단계에서 시간 변경 UI가 보이는 사례가 있으나 본 프로젝트는 **주문 완료 후 변경 불가**를 적용한다.
3. **배달중:** 지도에서 라이더 위치 마커, 배송 진행 상태, 갱신된 예상 도착 정보 표시.
4. **배송완료:** 배송현황 대신 완료 안내 및 주문상세에서 기록 조회. 분할배송이면 모든 배송 건이 완료된 이후에 주문 전체 완료로 표시.

<img src="images/screenshots/tracking-rider-live.jpg" alt="라이더 위치 표시 배달중 화면" width="400">

- 지도 출발지·도착지, 라이더 위치 및 실제 배송 예상 시간은 서버 배송 이벤트/위치 데이터에 연동한다.
- **분할배송:** 주문상세에 `배송 1/2`, `배송 2/2`처럼 배송 건별 진행 상태·담긴 품목·라이더/예상시간을 분리 표시한다. 배송 건마다 상태가 다를 수 있다.
- 예상 시간은 확정 도착 보증이 아니라 표시 당시 예측 정보이며, **주문 완료 시점의 배송 조건 확정**과 구분한다.
- 클릭이 반응하지 않는 `주문확인` 화면 사례가 있으므로, 링크가 제공되지 않는 상태와 실제 기능 오류를 분리해 검증한다.
- 주문 상태가 배송완료로 바뀐 뒤 옛 배송현황 링크에 접근하면 주문상세로 이동시키거나 완료 안내를 제공한다.

## 6. 주문 상태와 알림

### 6.0 주문내역·주문상세·문의하기 진입

<img src="images/screenshots/orders-list.jpg" alt="주문내역의 완료·예약 주문 목록" width="400">

<img src="images/screenshots/order-detail-pre-delivery.jpg" alt="배송 전 주문상세 화면" width="400">

- **주문내역:** 주문 이력이 없으면 빈 상태 안내를 표시하고, 주문 이력이 있으면 주문별 상품·주문 상태·예상/예약 도착 정보를 보여준다.
- **주문상세:** 주문상품·결제정보·배송정보 탭 또는 영역으로 세부 데이터를 확인한다. 배송완료 이후에는 현금영수증 버튼, 반품·교환, 문의하기와 같은 사후 기능이 나타난다.
- **같은 상품 담기:** 과거 주문의 상품을 **새 장바구니에 추가**하는 기능으로, 이미 완료된 주문을 수정하는 것이 아니다.
- **품절 상품:** 같은 상품을 다시 담을 수 없으면 품절 상태를 표시하고 비슷한 상품을 추천하는 화면 사례가 있다.
- **문의하기:** 상단 버튼 또는 스크롤 시 나타나는 플로팅 버튼에서 문의 사유를 선택한다.
- **주문 취소:** 주문의 `상품준비` 단계 이전까지는 주문 취소가 자유롭게 가능하다. **주문 정보 수정 불가**와 **주문 취소 허용 여부**는 서로 다른 정책이다.

<img src="images/screenshots/orders-out-of-stock-alternatives.jpg" alt="품절 상품과 대체 추천" width="400">

**프로젝트 결정:** 주문 완료 후 예약시간·배송지·연락처·라이더 요청 사항 등의 변경은 불가능하다. 단, 첨부 캡처에서 `예약시간 변경` 버튼이 보이는 것은 **화면 관찰** 사례이며 프로젝트 허용 정책이 아니다.

<img src="images/screenshots/reserved-time-edit-observed.jpg" alt="화면 사례에 나타나는 예약시간 변경(프로젝트 미지원)" width="400">

### 6.1 배송 완료와 알림 발송

```mermaid
flowchart TD
    A[라이더 앱 전달완료] --> B[배송완료 이벤트 수신]
    B --> C[주문 상태 배송완료 갱신]
    C --> D[알림 발송 이벤트 처리]
    D --> E[고객 푸시 수신 또는 앱 알림 목록 확인]
    E --> F[알림 선택]
    F --> G[주문 상세에서 최신 상태 조회]
```

- 라이더가 `전달완료`를 처리하면 주문이 `배송완료`로 갱신된다.
- 고객은 푸시 또는 앱 알림 목록에서 해당 주문을 확인한다.
- 발송된 알림 문구는 **발송 당시 상태**를 유지하지만, 알림을 통해 연 주문 상세는 **현재 상태**를 보여준다.

> **예시:** `배송중` 알림을 눌렀더라도, 현재 주문 상태가 `배송완료`라면 주문 상세에 `배송완료`를 표시한다.

### 6.1.1 분할배송 알림 집계

- 배송 건별 이벤트에는 `shipment_id`를 포함해 같은 주문에서 배송 1/2과 2/2의 알림을 구분한다.
- 배송 1/2만 완료되었다면 주문 전체의 `배송완료` 알림을 먼저 보내지 않는다. 필요하면 `일부 배송완료` 알림을 별도 발송한다.
- 모든 배송 건이 완료되면 주문 상태를 배송완료로 변경하고, 해당 주문의 최종 배송완료 알림은 **주문 단위로 한 번**만 생성한다.
- 알림을 열면 주문 상세에서 **최신 주문 상태 및 배송 건별 최신 상태**를 조회한다.

### 6.2 중복 알림·역행 방지

- 같은 주문의 같은 이벤트에 대해 동일 채널로 중복 알림을 보내지 않는다.
- 늦게 도착한 이전 상태 이벤트가 현재 주문 상태를 덮어쓰지 않도록 한다.
- 발송된 과거 알림의 문구를 최신 상태로 일괄 변경하지 않는다.
- 알림 자체를 눌러 상세 페이지에 진입하고 돌아온 뒤 읽음 상태를 반영하여 동작한다.

### 6.3 알림 권한과 종류

| 구분 | 의미 |
|---|---|
| OS 푸시 권한 | 운영체제에서 알림 수신 허용 여부 |
| 앱 내부 수신 동의 | 앱에서 설정한 알림 종류별 동의 여부 |
| 주문·배송 알림 | 주문 처리·배송 상태 등 서비스 정보 |
| 마케팅 알림 | 광고·이벤트·프로모션 정보 |

OS 푸시 권한이 없어도 고객은 **주문 내역에서 현재 상태를 조회**할 수 있어야 한다. 마케팅 알림 동의 철회는 마케팅 발송 중단으로 처리하고, 주문·배송 알림 정책과 분리한다.

### 6.4 알림 예외

- 알림이 없는 경우 빈 화면 안내
- 알림을 열었으나 주문 상세를 조회하지 못하면 재시도 안내
- 대상 주문이 없거나 접근 불가하면 안내 메시지 표시
- 잠금화면 메시지의 개인정보 노출 수준, SMS·이메일 추가 발송은 별도 결정

## 7. 반품과 환불

### 7.1 신청 경로와 기본 구분

> **프로젝트 결정 변경:** 과거(2021년) 반품 화면을 일반적인 상품 반품 신청 화면으로 해석하지 않는다. 해당 화면은 **반품 배달비 9,000원 옵션을 구매하는 페이지**로 정의한다. 실제 반품 사유 심사·회수·환불과는 별도 처리한다.

```text
주문내역 → 배송완료 주문상세 → 반품·교환
                              ├─ 교환 신청(별도 흐름)
                              └─ 반품 경로/반품 배달비 옵션 안내
                                      ↓
                              반품 배달비 9,000원 옵션 구매
                                      ↓
                              고객센터/운영자 반품 적격 심사·회수 판단
                                      ↓
                              회수·검수(필요 시) → 환불 심사·결제 처리
```

<img src="images/screenshots/delivered-return-exchange-contact.jpg" alt="배송완료 주문상세의 반품·교환/문의하기 버튼" width="400">

- **화면 관찰:** 배송완료 주문상세에서 `반품·교환`, `문의하기`가 제공된다.
- **프로젝트 결정:** 반품 관련 9,000원 페이지의 역할은 **반품 배달비 옵션 구매**다. 구매 즉시 환불 완료로 취급하지 않는다.
- **구현 제안:** 상품 하자·오배송 등 고객 귀책이 아닌 경우에는 배달비를 부과하지 않도록 사유별 유상/무상 기준을 별도로 확정한다.
- **미결정:** 반품 배달비 결제를 별도 주문/결제 거래로 처리할지, 본 주문에서 차감할지, 반품 거절·미회수 시 이미 수납한 배달비를 어떻게 정산할지.

**참고 링크:** [2021년 반품 화면 참고 자료](https://blog.naver.com/heartfelt10/222272871225). 외부 글의 본문 이미지는 직접 검증하지 못했으므로, 9,000원 옵션 구매라는 해석은 **이번 프로젝트 결정**으로 명시한다.

### 7.2 고객센터 접수 정보

- 주문번호, 주문일자, 배송완료 여부
- 주문 상품과 수량, 실제 결제 금액
- 적용된 쿠폰·할인과 기존 교환·환불 이력
- 반품할 품목·수량, 사유·상세 설명·사진
- 배송되지 않은 상품은 일반 반품이 아닌 **미배송 환불**로 분리

### 7.3 반품 사유

| 유형 | 사유 예시 | 원문 기재 증빙 |
|---|---|---|
| 변심·실수 | 마음에 들지 않음, 잘못 주문, 주소 설정 오류 | 상세 이유·사진 선택 |
| 상품문제 | 설명과 다름, 기능 문제, 변질, 이물질, 소비기한 경과 | 상세 이유·사진 필수 |
| 배달 문제 | 파손, 오배송, 일부 미배송, 배달완료인데 미수령 | 상세 이유·사진 필수 |

위 필수 여부는 문서에 정리된 초안이며, 반품의 경우 **운영 정책 확정 필요 항목**에도 포함되어 있다.

### 7.4 회수와 환불

1. 고객센터가 회수 필요 여부 판단
2. 필요하면 회수 상품·수량을 정하고 라이더 회수 업무 생성. 분할배송이라면 품목이 실제 어느 `shipment_id`로 배송되었는지도 연결
3. **회수지는 주문 당시 배송지로 고정**하며 주소 변경 불가. 해당 주소 기준으로 회수 요청 사항만 입력
4. 회수 완료 여부 기록 또는 회수 생략 사유 기록
5. 고객이 실제 지불한 금액과 적용 혜택을 고려해 환불 금액 산정
6. 기존 결제 수단 기반 환불/취소 요청과 결과 기록
7. 고객에게 환불 예정 금액·처리 결과 안내

> **정산 주의:**품절 시 **기존 결제 전체 취소 → 품절분을 제외한 금액으로 재결제**한 참고 사례가 있다. 그러나 이것을 프로젝트의 기본 반품·환불 정책으로 결정한 것은 아니다. 부분 결제취소 미지원 방침 아래 재결제 동의·실패·쿠폰 복원 등 후속 설계가 필요하다.

### 7.4.1 반품 배달비 옵션과 환불금 분리

- **프로젝트 결정:** 9,000원은 일반 환불액이 아니라 **반품 회수 배달비 옵션 구매 금액**으로 구분한다.
- 본래 상품 결제 거래, 반품 배달비 옵션 거래, 최종 환불 거래는 서로 참조하되 각각 거래 식별자를 둔다(구현 제안).
- 이미 반품 배달비 옵션을 구매했다고 해서 반품 승인/환불 금액이 자동 결정되는 것은 아니다.
- 회수 주소 변경은 불가능하며, 주문 당시 배송지 이외의 주소로 회수 접수되지 않도록 서버에서도 검증한다.

### 7.5 반품 상태

`접수` → `확인 중` → (`회수 대기` → `회수 중` → `회수 완료`) → `환불 처리 중` → `환불 완료`

- 회수가 필요 없는 경우 회수 단계를 건너뛸 수 있다.
- 가능 여부 심사에서 `반품 거절`로 종료할 수 있다.

> 실제 B마트의 상태 체계로 확인된 것은 아니다.

### 7.6 고객 안내

접수 여부, 거절 사유, 회수 상태, 환불 예정액·완료 결과를 안내하고 주문 상세에서 처리 내역을 확인할 수 있도록 한다.

### 7.7 배송완료 주문에서의 고객 문의 분기

<img src="images/screenshots/delivered-contact-choices.jpg" alt="배송완료 후 문의 유형 선택" width="400">

<img src="images/screenshots/delivered-delayed-report.jpg" alt="배송 지연 문의 사유 화면" width="400">

배송완료 주문의 `문의하기` 진입 후 `배달이 다른 길로 돌아서 늦었어요`, `입력한 주소와 다른 곳으로 배달됐어요`, `그 외 문의` 등 사유별 선택 화면을 확인할 수 있다. 지연 문의는 이유 선택 (두번째 이미지), 오배송 문의는 주문 당시 입력 주소와 라이더가 찍은 사진이 맞는지 검증과 라이더 통화·실시간 채팅상담 등 후속 동작이 나타난다.

> 배송중 주문 화면에는 다른 선택지가 보여질 것으로 예상한다.

고객 문의의 유형을 지연·오배송·품질·기타로 분류하여 상담 작업함에 등록하고, 반품·교환·재배달·환불과 연결한다. 고객 문의 접수 자체가 곧바로 PG 환불을 실행하지 않도록 상태를 분리한다.

## 8. 교환

### 8.1 신청 조건과 흐름

원문에 정리된 교환 조건:

- **배송 완료 이후** 신청 가능
- **상온 제품:** 단순 변심·실수 교환 허용
- **냉장·냉동 식품:** 단순 변심·실수 교환 제한
- **신선보장 제품:** 신선하지 않은 경우 교환 가능

```text
주문내역 → 교환 신청 → 대상 상품 선택(전체 선택 가능)
        → 교환 사유 선택 → 배달팁 확인
        → 회수·재배달 정보 및 요청 사항 작성
        → 접수 → 라이더 회수 및 교환 상품 재배달
```

### 8.2 교환 사유

| 유형 | 주요 선택 사유 | 상세 이유·사진 |
|---|---|---|
| 변심·실수 | 마음에 들지 않음, 잘못 주문, 주소 설정 오류 | 선택 |
| 상품문제 | 설명 다름, 기능 문제, 변질, 이물질, 소비기한 경과 | 필수 |
| 배달 문제 | 파손, 오배송, 일부 미배송, 배달완료 후 미수령 | 필수 |

### 8.3 회수·재배달 및 배달팁

- 교환 방법은 **라이더가 회수·재배달**하는 방식이다.
- 분할배송으로 수령한 품목도 교환 신청은 원 주문에서 시작하되 회수 대상 배송 건과 주문 품목을 연결해 추적한다.
- 기존 상품 회수 요청 사항과 새 상품 재배달 요청 사항을 **별도 작성**한다.
- **프로젝트 결정:** 회수지는 주문 당시 입력한 배송지로 **고정하며 변경 불가능**하다. 재배달 주소·연락처를 주문 완료 후 변경하는 것도 불허한다. 회수·재배달 요청 문구는 주소 변경 기능과 구분한다.

| 교환 사유 | 원문에 기재된 교환 배달팁 |
|---|---:|
| 변심·실수 | 9,000원 |
| 상품문제 | 무료 |
| 배달 문제 | 무료 |

**결정 완료 사항**

- 여러 상품을 교환할 때 사유는 **신청 전체 공통**으로 적용
- 동일 주문건의 **중복 교환 신청 불가**
- **회수지 변경 불허**
- 회수·재배달 요청 사항은 **자유 입력, 35~40자**라고 기재되어 있으나 단일 최대 글자 수는 아직 명확하지 않음

## 11. DB 연결 관계 및 공통 설계

### 11.1 범위와 모델링 전제

- **DB 기준:** MySQL 8.x 관계형 DB를 가정한 **초기 논리 설계**다. 실제 운영 DB 확정 전 테이블·컬럼·제약은 팀과 합의한다.
- **데이터 구분:** 마스터(`customers`, `products`, `delivery_methods`), 현재 상태(`center_inventory`, `carts`), 주문 스냅샷(`orders`, `order_items`), 처리 이력(`payment_attempts`, `shipment_events`, `order_status_history`), 사후 처리(`claims`, `refunds`)를 분리한다.
- **시점:** 조회/장바구니 추가 시 표시된 재고·배송 시간은 확정 데이터가 아니다. **결제 승인 성공을 확인하고 주문 완료를 반영할 때** 재고·배송 슬롯 확정을 한 번 수행하도록 멱등성 있게 설계한다. 예약·동시성 확보를 위한 임시 홀드 도입 여부는 별도 결정한다.
- **스냅샷:** 주문 품목의 단가·중량과 주문 배송지는 확정 시점 값을 보존한다. 이후 상품 마스터/기본 배송지가 바뀌어도 과거 주문을 변경하지 않는다.
- **분할배송:** `orders (1) → shipments (N) → shipment_items (N)`이며 상품별 합계 수량은 원 주문 수량과 같고 배송 건 중량은 각각 10,000g 이하다. `orders.total_weight_g > 10000`이면 `split_required = true`다.
- **결제:** 원 주문의 결제 의무는 주문 금액 한 번으로 관리한다. 분할배송으로 결제 승인 횟수 또는 봉투값을 배송 건 수만큼 늘리지 않는다. 별도 배송비 여부는 미결정이다.
- **명칭:** PK는 `*_id`, 참조는 동일한 FK명, 등록일자는 `created_at` 또는 `registered_at`을 사용한다. 실제 테이블에는 공통 감사 컬럼(`created_at`, `updated_at`, `created_by`)을 필요에 따라 추가한다.

### 11.6 실제 구현 전 검증 항목

| 구분 | 서버 검증 및 데이터 제약 |
|---|---|
| 구매 상한 | `1 <= cart_items.quantity <= products.max_order_qty`, `max_order_qty` 기본 10, 상품별 변경 가능; 주문 생성 시 재검증 |
| 중량 합계 | `orders.total_weight_g = SUM(order_items.quantity * order_items.unit_weight_g)` |
| 분할 여부 | `orders.split_required = (orders.total_weight_g > 10000)` |
| 배송 무게 | `SUM(shipment_items.allocated_weight_g)` = 해당 `shipments.shipment_weight_g`, 각 건 10,000g 이하 |
| 수량 정합성 | 주문 확정 후 `SUM(shipment_items.allocated_qty)` = 각 `order_items.quantity` (할당 진행중 상태는 예외) |
| 금액 | `orders.pay_amount = item_amount + delivery_fee + bag_fee` (추가 할인이 있다면 item_amount에 반영한 기준) |
| 첫 구매 혜택 | 서버에서 취소/환불 주문 포함 기준 합의 후 결제 직전 판정 |
| 결제 멱등성 | 토스 승인/취소 요청마다 멱등성 키를 적용하고 PG 결과 불명확 시 조회 우선 |
| 주문 상태 집계 | 배송 건 일부 완료는 주문 전체 `DELIVERED`로 집계하지 않음 |
| 회수지 고정 | 접수 시 원 주문의 배송지 스냅샷을 사용하며 수정 API를 제공하지 않음 |
| 환불 분리 | `claims` 상태와 `refunds` 결과가 다를 수 있고, 수납한 옵션 결제도 별도 추적 |

> **필수 인덱스 권장:** `cart_items(cart_id,product_id)` UNIQUE, `center_inventory(center_id,product_id)` UNIQUE, `orders(customer_id,created_at)`, `order_items(order_id)`, `shipments(order_id,shipment_no)` UNIQUE, `shipment_items(shipment_id,order_item_id)`, `notifications(customer_id,is_read)`, `payment_attempts(idempotency_key)` UNIQUE, `claims(order_id,claim_type)`.

### 11.7 트랜잭션 및 동시성 예시

```text
고객 장바구니 변경
  └─ 상품별 구매 상한(기본 10) 확인 → 선택 수량 임시 저장
주문서 생성/결제 인증 전
  └─ 가격·재고·배송 시간·총중량·배송 건수·배달팁 재계산
토스 인증 후 서버 승인
  └─ 서버 확정 주문번호/금액 비교 → 승인 요청(멱등성 키)
승인 성공 확인
  └─ 주문 상태 확정, 재고/예약 슬롯 실제 반영(한 번만)
  └─ order_items 주문 당시 가격·단위중량 스냅샷 저장
  └─ 10kg 초과면 shipments 여러 건 및 shipment_items 수량 배정
  └─ Outbox/이벤트로 피킹·배차·알림 연동
각 배송 건 배송완료
  └─ shipment_events 저장 → 미완료 배송 건 확인 → 전부 완료 시 주문 배송완료
```

> **구현 주의:** PG 승인 호출과 데이터베이스 트랜잭션은 하나의 원자적 트랜잭션으로 묶을 수 없다. 승인 성공 후 주문 확정 실패 시 보상·재처리 작업함이 필요하며, 이 설계는 결제 흐름 `4.1`의 화면/시퀀스 자체를 변경하지 않고 **실패 복구를 위한 내부 데이터 처리 상세**를 추가한 것이다.

> **샘플 데이터 사용 주의:** 기능별 임시 데이터는 테이블당 대표 3행만 제공한다. 이는 DB에 바로 실행하는 완결된 INSERT 시드가 아니다. 실제 샘플 DB를 구성할 때는 누락된 배송/상태 이력, 회원 과거 주문, 주문-배송지 스냅샷, 날짜 및 FK 연결 행을 모두 채우고 무결성 검사를 수행한다.
